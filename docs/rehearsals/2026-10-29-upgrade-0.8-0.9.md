# Rehearsal: 0.8 → 0.9 → rollback, on a copy of a 0.8 home (2026-10-29)

Made-up data only. The real 0.8 (`pins.json` `previous_core`, main at ccc7729) made a home with one vault, three
tags with fields or parents, eight notes and three keys (one tag-scoped to `#compost`). The home was copied, and
every step below ran on the copy with the 0.9.0-pre.1 candidate (b21eba3), inside its own network namespace so no
port of the machine's live service was touched:

```
unshare -rn bun docs/rehearsals/rehearse-upgrade-0.8-0.9.ts <0.8 bundle> <0.9 bundle> <scratch>
```

What it shows:
- 0.9's first command backed up both databases before opening them, outside the home.
- 0.9 served the home: 0.8's keys, including the tag-scoped one (still 2 notes visible), are listed by name; a tag
  with a parent is a type.
- `upgrade --rollback` refused while 0.9 was serving (exit 7); stopped, it was code-only and changed no vault byte.
- 0.8 then served every note and key 0.9 had made, and wrote its own; 0.9 picked those up (a new tag with fields
  became a type, a new token became a key), backing up again first.
- `--restore` exported the 2 notes written after the second backup, put the backup back, and 0.8 served it.
- The original 0.8 home's hash is the same at the end.
